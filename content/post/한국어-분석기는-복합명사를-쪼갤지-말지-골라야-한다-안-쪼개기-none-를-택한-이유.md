## TL;DR
한국어 형태소 분석기(nori)는 `오이소박이` 같은 복합명사를 **쪼갤지 말지**를 `decompound_mode`로 고른다. 쪼개면 부분명사 검색이 되는 대신 없는 말이 조각으로 걸린다. 실제 문서 4개로 재보고 **색인·검색 둘 다 ****`none`****(안 쪼갬)** 을 택했다. 근거는 ① 이 티켓이 오탐을 잡는 것이고 ② 색인 모드와 검색 모드가 다르면 오히려 못 찾기 때문.
앞선 노트 Elasticsearch는 검색어와 문서를 같은 방식으로 쪼개 대조한다의 후속. 거기서 "쪼개는 방식이 검색 품질을 결정한다"까지 갔다면, 이 노트는 "그럼 어떻게 쪼갤 건데"에 대한 답이다.
## 세 가지 모드
```javascript
none      오이소박이 → [오이소박이]                 // 안 쪼갬
discard   오이소박이 → [오이][소][박이]             // 쪼갠 조각만
mixed     오이소박이 → [오이소박이][오이][소][박이]   // 원형 + 조각
```
## 검증 방법
로컬 ES에 임시 인덱스 4개(ik 기준선 / none / discard / mixed)를 만들고 **같은 문서를 같은 방식으로 청크 내어 동일하게 색인**한 뒤, 검색어별 히트 수를 비교했다.
- 문서 4개(6·25 전쟁 / 장발장 / 김치 백과사전 / 전기차 전환 영문) = 103청크
- **정답지는 원문 등장 횟수** (`grep -o | wc -l`). 감이 아니라 숫자로 판정하려고
- 검증 축 3개: 복합명사 전체 / 부분명사만 / 원문에 없는 글자 조합
## mixed가 탈락한 이유 — 색인과 검색 모드가 다르면 안 맞는다
처음 잠정 결론은 "색인은 `mixed`(다 넣어두고) 검색은 `none`"이었다. 넣을 땐 많이, 찾을 땐 정확히 — 그럴듯했는데 실측에서 제일 나빴다.
```javascript
색인 mixed:  오이소박이 → [오이소박이][오이][소][박이]
검색 none:   소박이     → [소박이]      ← 저장된 조각에 없음 → 0건
```
저장된 조각과 검색어 조각은 **글자 그대로 같아야** 매칭된다. 모드를 다르게 두면 같은 단어라도 조각 모양이 달라져 어긋난다. 실제로 `한국학중앙연구원`(원문 2회)이 mixed/none에서 **0건**이 나왔다.
→ **색인 analyzer와 검색 analyzer는 같은 걸 쓴다.** 다르게 쓸 이유가 생기면 그때마다 실측해야 한다.

**교훈**: 지표가 비기면 "어느 쪽이 더 좋은가"가 아니라 **"지금 무슨 문제를 풀고 있나"** 로 가른다.
## 매칭 규칙도 같이 바꿔야 했다 — 공백 유무로 분기
분석기만 바꿔서는 부족했다. `김치물`(없는 말)이 `[김치]`+`[물]`로 쪼개져 둘 다 있는 청크에 걸렸다.
```python
한 단어      → type: phrase     # 조각이 붙어 있어야 함
띄어 쓴 여러 단어 → operator: and    # 단어가 다 있으면 됨
```

<td>0</td>

<tr>

<td>7</td>
<td>0</td>
<td>7</td>
</tr>
<tr>
<td>도마뱀 서식지</td>
<td>4</td>
<td>0</td>
<td>4</td>
</tr>
</table>
- `and`만 쓰면 한 단어가 조각으로 쪼개져 없는 말이 걸린다
- `phrase`만 쓰면 조사 때문에 2어절이 죽는다 (원문은 "오늘날**의** 김치")
- `slop: 1`(단어 사이 한 칸 허용)도 재봤지만, 두 단어가 좀 떨어져 있는 정당한 결과(`도마뱀 서식지` 4건)를 0건으로 죽여서 탈락
구글과 같은 규칙이다. `김치물`을 치면 김치 문서를 주지 않고, `배추 김치`를 치면 둘 다 있는 문서를 준다.
## 알려진 한계 3가지 (측정해서 아는 것)
**① 영어 단수/복수가 서로 안 잡힌다**

nori는 한국어 분석기라 영어 어간 처리(stemming)를 하지 않는다. `insights`를 `insight`로 정규화해주지 않는다.
**중요한 건 이게 회귀가 아니라는 것.** 이전 ik로 같은 문서를 재보니 숫자가 완전히 같았다. 원래부터 안 되던 것이고 이번 변경이 건드린 부분이 아니다. → **"나빠 보인다"와 "내가 나쁘게 만들었다"는 다르다. 바꾸기 전 상태로 같은 측정을 해봐야 안다.**
고치려면 영어 전용 서브필드(`content.en` + english analyzer)를 추가해야 하는데, 어간을 자르면 `note`로 `notes`·`noted`·`noting`이 다 걸려 **정밀도가 내려간다**. 오탐을 잡는 이번 작업과 방향이 반대라 후속으로 분리했다.
**② 복합명사의 일부만 치면 안 나온다** — `오이소박이` 문서에 `소박이` 검색 → 0건. `none`을 택한 대가.
**③ 한 글자 외래어가 조사로 오인될 수 있다**
```javascript
"장편소설 《레 미제라블》에"
   레 → J(조사)    ← 품사 필터가 버림
```
`레`가 색인에 안 들어가서 `레 미제라블` 검색이 0건이 된다(`미제라블`은 2건 정상). 품사 필터를 빼면 고쳐지지만 활용형 검색(`나온다`로 "나오는" 찾기)이 죽어서 그대로 뒀다.
## 다시 하면 이렇게 할 것
- **잠정 결론은 데이터 보기 전 가설일 뿐이다.** mixed/none은 그럴듯했지만 재보니 최악이었다
- 정답지를 먼저 정한다. 여기서는 원문 등장 횟수. 없으면 결과를 보고 사후에 합리화하게 된다
- 규칙을 바꿨으면 **앞서 내린 결정도 다시 잰다.** 매칭 규칙을 phrase/and로 바꾼 뒤 모드 비교를 다시 돌렸더니 모드 간 차이가 크게 줄어 있었다. 안 다시 쟀으면 낡은 근거로 결정할 뻔했다
