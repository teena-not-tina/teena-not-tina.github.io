[① 도입 이유와 호출·키 관리]({{< relref "post/litellm-sdk-proxy-virtual-key-캐시-이해하기.md" >}}) · **② 기능 실행과 모델 사용량 관측** · [③ 공급망 사고와 의존성 관리]({{< relref "post/litellm-supply-chain-security.md" >}})

사용자는 기능을 한 번 실행했는데 모델 호출은 여러 건으로 기록될 수 있다. 반대로 캐시에서 결과를 돌려주면 기능은 실행됐어도 새로운 모델 호출이 없을 수 있다.

그렇다면 “사용량”은 무엇을 세어야 할까? 이 글에서는 **모델 요청의 기록을 업무 기능의 실행 맥락에 연결하는 방법**과 토큰·비용·캐시를 읽는 기준을 정리한다. SDK·Proxy와 Virtual Key의 기본 역할은 1편에서 설명했다.

> 기능 설명의 확인 기준은 2026-11-09이다. 부서·서비스·모델명과 수치는 가상 예시이며 특정 회사의 내부 구조나 운영 지표를 재현하지 않는다.

## 먼저 집계 단위를 나눈다

모델 비용과 도구 사용량, 공급자의 청구와 고객 판매 가격, UTC 기록과 고객의 하루는 서로 다른 개념이다. LiteLLM이 제공하는 원본 기록을 앱의 지표로 해석하는 과정에서 데이터 원천과 집계 단위를 정해야 한다.

부서별 예산을 보고 싶다면 어느 부서가 사용했는지, 기능을 분석하려면 어떤 작업과 단계에서 호출했는지가 필요하다. 같은 기록도 질문에 따라 묶는 기준이 달라지므로, 모델 요청·기능 실행·비용을 하나의 수치로 뭉뚱그리지 않는 데서 출발한다.

## 모델 호출 기록에 앱의 실행 맥락을 연결하기

Proxy에 DB 저장을 구성하면 LiteLLM은 호출한 모델, 토큰 사용량, 계산 비용, 사용자·팀·키 정보와 요청 태그 등을 기록할 수 있다. 사용자별·팀별 사용량을 집계하는 기능도 제공한다. [Spend Tracking 문서](https://docs.litellm.ai/docs/proxy/cost_tracking)에 기록 예시가 있다.

이 기록을 앱의 기능 사용량으로 읽으려면 추가 맥락이 필요하다.

![마케팅 초안 생성 1회 안에서 모델 요청 3건이 발생하고 실행 식별자로 연결하는 가상 예시](/img/litellm-study-usage-context.svg)

가령 마케팅 초안 생성 기능을 한 번 실행하는 동안 요청 정리, 초안 작성, 표현 검토에 각각 모델을 호출한다고 가정해 보자. LiteLLM은 각 모델 요청의 토큰과 비용을 기록할 수 있지만, 세 요청이 같은 초안 생성 작업에 속한다는 정보는 앱이 전달해야 한다.

이를 위해 도구 이름, 실행 식별자, 내부 단계 이름 같은 메타데이터를 연결한다. 그러면 다음 지표를 구분할 수 있다.

- 고객이 도구를 실행한 횟수
- 도구 내부에서 실제로 모델을 호출한 횟수
- 각 내부 단계와 도구 전체에서 발생한 모델 사용량

특히 도구 실행을 요약한 행과 내부 모델 호출 행을 함께 저장한다면 같은 사용량을 두 번 세지 않도록 집계 단위도 정해야 한다.

“도구가 내부에서 다시 호출됐는지 LiteLLM은 알 수 없는가?”도 비슷한 질문이다. 기본 모델 요청 기록만으로 앱 내부의 호출 관계를 복원할 수 있다고 기대하면 안 된다. 상위 실행·하위 단계의 관계를 앱에서 식별하고 전달하면 연결해서 분석할 수 있다. 도구나 추적 연동으로 더 많은 맥락을 기록할 수 있어도, 서비스의 작업 경계를 정의하는 일은 남는다.

### 사용량 관측과 응답 품질 평가는 다르다

토큰을 많이 썼다는 사실만으로 좋은 답변인지 알 수는 없다. 비용과 호출 수를 관측하는 것은 효율과 원인 분석을 위한 기반이고, 답변 품질은 별도의 평가 기준이 필요하다.

예를 들어 고객이 “검색이 느리다”고 했을 때 전체 응답 시간만 보면 모델이 느린지, 검색 도구를 여러 번 호출했는지, 실패와 재시도가 있었는지 구분하기 어렵다. 실행 식별자로 도구와 모델 요청을 연결하면 어느 단계를 조사할지 범위를 좁힐 수 있다. 하지만 정답성이나 근거의 적절성까지 판단하려면 평가 데이터와 실행 결과를 따로 비교해야 한다.

따라서 모델별 비용 집계만으로 Agent Observability 전체를 구현했다고 표현하기보다는, **비용과 사용량을 실행 맥락에 연결하는 관측 기반**이라고 설명하는 편이 정확하다.

### 사용량 로그에서 구분해서 읽을 항목

| 항목 | 읽을 때의 질문 |
|---|---|
| 모델 이름·모델 그룹 | 어떤 모델 또는 모델 이름으로 요청했는가? |
| 키 식별값·키 별명 | 어떤 인증 정보로 요청했는가? 별명이 실제로 있는가? |
| 사용자·팀 | 누구·어느 팀의 사용량으로 연결됐는가? |
| 입력·출력 토큰과 비용 | 사용량과 가격 설정에 따라 얼마로 계산됐는가? |
| 요청 태그 | 어떤 작업·도구·실행의 요청이라고 앱이 전달했는가? |

키 식별값과 모델 이름은 역할이 다르다. 키의 표시 방식이나 별명 유무는 인증 방식과 설정에 따라 달라질 수 있다. 식별값만 보고 모델의 이름이나 사용자의 신원까지 추정해서는 안 된다.

실제 로그를 공개할 필요 없이 다음처럼 줄여도 읽는 법을 설명할 수 있다. 아래 값은 모두 가상이다.

```text
call_type:   acompletion
model:       provider/model-A
prompt:      100 tokens
completion:  20 tokens
key_alias:   marketing-demo
tags:        ["department:marketing", "task:draft-demo"]
```

이 예시에서 확인할 수 있는 것은 비동기 응답 생성 호출, 모델 이름, 기록된 토큰, 키의 별명과 앱이 전달한 태그다. `marketing-demo`라는 키의 별명과 `model-A`라는 모델 이름은 서로 다른 값이다. 실제 기록을 해석할 때는 각 필드의 정의와 전달 경로를 확인해야 한다.

비용도 구분해서 읽어야 한다. 모델 가격 설정에 따라 계산한 비용이 제공자의 최종 청구서와 항상 같은 것은 아니다. 특히 자체 운영 모델의 가격을 0으로 설정했다면 로그상 비용이 0이어도 서버 운영 비용까지 없다는 뜻은 아니다.

단순한 토큰 가격 모델이라면 입력 토큰 수에 입력 단가를, 출력 토큰 수에 출력 단가를 곱해 더한다. 예를 들어 입력 2,000토큰, 출력 100토큰이고 단가가 각각 100만 토큰당 0.25달러·1.50달러라고 가정하면 계산 비용은 0.00065달러다. 실제 모델의 가격을 인용한 예시가 아니라 계산 방식을 설명하기 위한 가상 값이다.

실제 기록에서는 캐시된 입력이나 reasoning token 등 토큰 종류와 가격 규칙을 함께 봐야 한다. 상세 필드가 상위 토큰 수의 일부라면 이를 다시 더할 때 중복이 발생할 수 있다. 토큰의 세부 분류, 가격 맵, 기록 누락 여부와 비교 기간을 확인한 뒤 공급자 청구와 대조해야 한다. 비용 필드 하나를 고객 청구액과 바로 같은 값으로 해석하지 않는 이유다. [공식 비용 추적 문서](https://docs.litellm.ai/docs/proxy/cost_tracking)

### 앱이 정해야 하는 귀속과 집계 기준

LiteLLM에 팀별 기록 기능이 있어도, 어떤 팀을 기록해야 하는지는 앱의 규칙이다. 예를 들어 한 직원이 여러 부서의 업무를 지원한다면, 사용자 한 명의 합계만으로는 어느 부서의 업무에 비용이 들었는지 구분하기 어렵다. 부서용 키를 나누거나 작업의 소속 정보를 연결하는 등 목적에 맞는 기준을 정해야 한다.

날짜도 같다. 저장 시각이 UTC라면 한국 사용자가 선택한 하루에 해당하는 조회 구간을 정해야 한다. 이미 합산한 UTC 일별 수치를 화면에서 시각만 바꾼다고 한국 날짜의 합계가 되는 것은 아니다.

이런 기준은 부서별 예산과 기능별 사용 패턴을 해석하는 데 필요하다. 다만 모델 호출 비용이 제품의 판매 가격과 같은 것은 아니다. 저장소·인프라·지원 비용이나 제품 가치까지 자동으로 계산해 주지는 않는다.

## 캐시는 이전 호출 결과를 재사용한다

같은 조건의 요청에 매번 모델을 실행하면 시간과 비용이 반복해서 든다. 캐시는 한 번 얻은 결과를 저장해 뒀다가 재사용할 수 있는 요청에 돌려주는 기능이다.

![첫 요청은 모델을 호출해 결과를 저장하고 같은 조건의 다음 요청은 캐시에서 결과를 반환하는 흐름](/img/litellm-study-cache.svg)

| 용어 | 의미 |
|---|---|
| Cache miss | 재사용할 결과가 없어 실제 모델 호출이 필요한 상태 |
| Cache hit | 저장된 결과를 찾아 재사용하는 상태 |
| Cache key | 어떤 요청의 결과인지 구분하는 식별자 |
| TTL | 저장한 결과의 유효기간 |

예를 들어 변하지 않은 문서를 같은 모델과 조건으로 반복 요약할 때, 이전 결과를 그대로 써도 된다면 모델에 다시 요청할 필요가 없다. 반면 최신 상태가 중요한 자료, 매번 새 결과를 기대하는 생성 작업, 사용자마다 권한과 문맥이 다른 요청에서는 재사용 범위를 신중히 정해야 한다.

같은 질문 문장이라는 이유만으로 같은 요청은 아니다. 대화 이력, 입력 문서, 모델과 생성 조건 등이 다르면 결과도 달라질 수 있으므로 캐시의 식별 기준을 고려해야 한다.

캐시는 대화 메모리나 모델 학습과도 다르다. 캐시는 저장해 둔 결과를 다시 돌려주고, 대화 메모리는 다음 요청에 필요한 맥락을 유지하며, 학습은 모델의 파라미터를 바꾸는 과정이다. “기억한다”는 표현으로 묶으면 무엇이 재사용되는지 헷갈리기 쉽다.

여기서 설명한 것은 완성된 응답을 재사용하는 캐시다. 모델 제공자가 입력 프롬프트 일부의 처리 결과를 재사용하는 prompt caching과는 구분한다. [LiteLLM 캐시 문서](https://docs.litellm.ai/docs/caching/all_caches)도 두 기능의 문서를 따로 안내한다.

캐시를 도입할 때는 저장 방식, TTL, 적용할 요청 범위를 정하고 실제 적중률과 지연·비용 변화를 확인해야 한다. 캐시를 지원한다는 사실만으로 운영 환경에서 활성화돼 있거나 절감 효과가 검증됐다고 볼 수는 없다.

프록시 로그에 `Cache OFF`라고 표시돼도 앱 내부 SDK 캐시까지 모두 꺼져 있다고 단정할 수는 없다. 앱의 캐시에서 요청이 끝나면 프록시까지 도달하지 않을 수도 있으므로, 어느 계층의 캐시를 보고 있는지 구분해야 한다.

캐시가 잘못된 결과를 계속 재생할 수도 있다. 본문이 없는 응답을 저장하면 같은 작업을 재시도해도 모델을 다시 호출하지 않고 빈 결과를 받을 수 있다. 오류 응답이나 비어 있는 결과를 저장할지 판단하고, 저장한 결과를 무효화할 기준도 정해야 한다.

캐시에서 결과를 반환한 도구 실행은 새로운 모델 호출을 발생시키지 않을 수 있다. 따라서 고객의 기능 사용 횟수와 실제 모델 사용량을 따로 해석해야 한다.

## 기록을 지표로 만들 때 확인할 것

모델별 토큰과 비용은 호출의 크기를 보여 주고, 실행 식별자와 단계 정보는 그 호출이 왜 발생했는지 해석하는 단서가 된다. 부서·업무별 지표를 만들려면 이 둘을 연결하면서 중복 집계와 날짜 경계를 확인해야 한다.

운영에서 효과를 검증하려면 실제 사용량과 비용 계산을 대조하고, 캐시 적중률과 지연 변화도 측정해야 한다. 계측 기능을 지원한다는 것과 서비스에서 정확한 지표를 제공한다는 것은 다른 일이다.

다음 글에서는 이 공통 계층을 운영할 때 생기는 또 다른 책임, **배포물과 자격 증명의 보안**을 공급망 사고 사례로 살펴본다.
