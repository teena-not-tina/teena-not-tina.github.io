> **한 줄** — SMTP는 메일 발송 프로토콜. <br>로그는 로컬 → (컨테이너) → log collector → 중앙 log storage(정해진 기간 보관) → log dashboard로 흘러가고, 장애 조사 때 운영 담당자가 대시보드에서 확인할 수 있다. <br>그래서 쿼리스트링의 토큰 같은 비밀값은 **완전히 지우지 않고 값만 가리는** 절충을 한다.
## SMTP란
**S**imple **M**ail **T**ransfer **P**rotocol — 메일을 "보내는" 통신 규약. 우체국에 편지를 맡기는 것과 같다: <br>앱은 편지(메일 내용)만 쓰고, 실제 배달은 SMTP 서버(`smtp.example.com` 같은)가 한다.
```javascript
EMAIL_MAIL_SERVER=smtp.example.com   # 어느 우체국
EMAIL_MAIL_PORT=587                     # 창구 번호
EMAIL_MAIL_STARTTLS=true                # 봉투(암호화) 방식
```
포트 587(STARTTLS)과 465(SSL_TLS)는 암호화 "방식"이 달라서 반드시 짝을 맞춰야 한다 — 창구 번호와 그 창구의 접수 절차가 안 맞으면 처리가 안 되는 것과 같다.
## 로그가 가는 경로
```mermaid
flowchart LR
  App["앱 (structlog)"] -->|로컬| Console["터미널 / app.log"]
  App -->|배포 환경| Log collector["log collector"]
  Log collector --> log storage["중앙 log storage (정해진 기간 보관)"]
  log storage --> log dashboard["log dashboard (조회)"]
```
## 누가, 언제 볼 수 있나
> **로컬 개발 중**: 개발자 본인이 자기 터미널에서 바로 봄. 접근 제어랄 게 없음(내 화면).
> **서버 접근 권한자**: `app.log` 파일이나 `docker logs`로 직접 봄. SSH·배포 인프라 권한이 있는 사람만.
> **log dashboard 로그인 권한자**: 장애·버그 조사 때 담당자가 log dashboard에서 특정 유저의 요청 로그를 검색해서 봄. 가장 흔한 경로.
**핵심 위협 모델**: "권한 밖의 사람이 훔쳐본다"가 아니라 **"로그를 볼 정당한 권한이 있는 팀원도 이 값까진 보면 안 된다"**는 것. 로그 열람 권한 ≠ 계정 탈취 권한이어야 한다.
## 왜 값만 가리고 완전히 지우진 않나
로그를 남기는 목적(디버깅) 자체는 그대로 두고, 그 목적에 불필요한 부분(비밀값)만 없앤다.
- `token` 파라미터가 **아예 없다** → 링크가 깨져서 왔나?
- `token=***`로 **있기는 하다** → 토큰은 왔는데 값이 무효/만료됐나?
이 둘은 원인이 다른데, 값을 통째로 지우면 이 구분 자체가 불가능해진다. 그래서 "민감한 값만 가리고 파라미터가 존재했다는 구조는 남긴다."
## 테스트로 고정한 것
마스킹 테스트 — 실제 HTTP 요청을 보내고 미들웨어가 만드는 로그 컨텍스트를 가로채서 세 가지를 확인한다:
1. 원본 토큰 값이 로그 어디에도 없다
2. `token=***`로 마스킹돼 있다 (마스킹이 실제로 걸렸는지)
3. `page=3`(민감하지 않은 값)은 그대로 남아있다 (과하게 다 가리지 않았는지)
단위 테스트로 마스킹 함수만 검증하지 않고, **미들웨어를 통해 실제 요청 흐름에서** 검증한 것이 포인트.
## 신입이 기억할 핵심
> 로그 보안은 "다 지우기" vs "다 남기기"의 양자택일이 아니다. **로그의 목적(디버깅)을 지키면서 그 목적에 불필요한 비밀값만 제거**하는 절충점을 찾는 것 — 이게 마스킹 설계의 핵심 패턴.
