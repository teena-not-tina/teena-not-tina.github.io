## TL;DR
ES는 원문을 통째로 비교하지 않는다. **저장할 때 문서를 조각(토큰)으로 쪼개 역색인에 넣고, 검색할 때 검색어도 같은 방식으로 쪼개서 조각이 글자 그대로 같은지**만 본다. 그래서 쪼개는 방식(analyzer)이 검색 품질을 결정한다. 언어가 여럿이면 필드를 언어별로 나눠 각각 쪼개 저장하고, 검색할 때 여러 필드를 함께 조회한다.
## 역색인(inverted index)
"문서 → 단어"가 아니라 **"단어 → 그 단어가 들어 있는 문서 목록"** 으로 뒤집어 저장한 표. 검색어로 표를 한 번 찾으면 문서 목록이 바로 나와서 빠르다.
```javascript
서식지  →  청크 2, 청크 4
도마뱀  →  청크 2
```
## 양쪽 다 쪼갠다 (여기가 핵심)
```javascript
저장: "도마뱀의 서식지" → [도마뱀][의][서식지]   ← 역색인에 이 조각들이 들어감
검색: "도마뱀"          → [도마뱀]               ← 이 조각으로 표를 조회
```
양쪽을 **같은 analyzer로** 쪼개야 대조가 성립한다. 비슷한지 판단하는 게 아니라 **완전 일치**만 본다.
## 실제로 겪은 버그 (테스트 환경)
예시 인덱스가 중국어용 analyzer(ik)를 쓰고 있어서 한글이 한 글자씩 쪼개졌다.
```javascript
"도마뱀" → [도][마][뱀]
```
여기에 "조각 하나만 맞아도 결과에 포함"(multi_match 기본값 best_fields) 규칙이 겹쳐서, **글자를 붙일수록 결과가 늘어나는** 현상이 생겼다.
실측: 82청크 문서에서 `도마뱀` 검색 56개, 글자 순서만 섞은 **없는 단어** `뱀마도`도 **똑같이 56개**. 사실상 검색이 동작하지 않는 상태였다.
## 귀결 — analyzer를 바꾸면 재색인이 필요하다
이미 저장된 조각은 옛 방식으로 쪼개져 있다. 매핑만 바꾸면 검색어는 새 방식으로 쪼개지는데 저장된 조각과 안 맞아 **아무것도 안 나온다**.
다만 원문이 ES 안에 남아 있어서 `_reindex`로 다시 쪼개 넣으면 된다. **문서 재업로드나 재파싱은 불필요**하다.
## 색인해도 바로 안 보인다 — refresh
ES는 문서를 넣어도 **즉시 검색에 보이지 않는다.** 잠깐 버퍼에 담아뒀다가 주기적으로(기본 1초) 정리하면서 그때부터 검색 대상이 된다. 그 "정리해서 보이게 하기"가 `refresh`다. 한 건마다 즉시 반영하면 느려서 모아 처리하는 것.
```python
es.index(문서)      # 저장은 됨. 아직 검색에 안 보임
                    # ↓ 1초 뒤 자동, 또는 es.indices.refresh()
es.count()          # 이제 보임
```
### 실제로 데이터를 날릴 뻔한 지점 (2026-08 재색인)
analyzer를 바꾸면 재색인이 필요한데, 인덱스 이름이 고정되어 있어 **백업 인덱스를 경유해 왕복**해야 했다. 원본 → 백업 → (원본 삭제·재생성) → 원본. 첫 복사 직후 refresh를 빼먹었더니:
```javascript
_reindex 원본 → 백업     56건 복사됨
백업 건수 조회            0건    ← 아직 안 보임
백업을 source로 다시 복사  0건 복사   ← 에러 없이 조용히 빈 복사
```
**에러가 안 난다는 게 핵심이다.** ES는 "복사 완료"를 정상 응답으로 돌려주고, 다음 단계가 빈 인덱스를 읽는다. 원본을 이미 지운 뒤였다면 그대로 유실이었다.
귀결: **`_reindex`**** 결과를 다음 단계의 source로 쓰기 전에 반드시 ****`refresh`**** + 건수 대조.** 대조를 넣어두면 refresh를 빼먹어도 멈춘다.
### 세는 쪽에도 같은 함정이 있다
리뷰에서 짚혀 알게 된 것 — **원본을 셀 때도 refresh가 필요하다.** 청크 색인 코드가 refresh를 하지 않아서, 문서를 올린 직후 1초 안에 재색인을 돌리면 원본이 실제보다 적게 세진다. 그러면 복사본이 더 많아 보여 건수 대조가 실패하고, **멀쩡한 인덱스가 실패로 처리된다.**
"복사한 쪽만 refresh"로는 부족하고, **건수를 세는 모든 지점**에 필요하다.
### 관련 API
- `_reindex`는 개별 문서가 실패해도 **예외를 던지지 않는다.** 200 응답의 `failures` 배열에 담아 돌려주므로 직접 확인해야 한다
- 복사할 문서가 0건이면 `_reindex`는 **대상 인덱스를 만들지 않는다.** 뒤따르는 조회가 404가 된다
- `dest`를 미리 만들지 않으면 dynamic mapping으로 생성된다. 원본에서 `enabled: false`로 검사하지 않던 필드까지 색인하려 들어, 문서마다 타입이 다르면 복사가 깨진다
## 다국어 — 필드 하나에 analyzer 하나
한 필드에는 analyzer를 하나만 붙일 수 있다. 그래서 언어가 여럿이면 같은 텍스트를 **언어별 필드에 각각 색인**한다.
```javascript
content      ← nori(한국어)     → [도마뱀][의][서식지]
content.ja   ← kuromoji(일본어) → [도마뱀의][서식지]
```
kuromoji는 한글 사전이 없어서 한글을 어절 통째로만 쪼갠다. 원문은 한 번만 저장되고 **역색인만 두 벌** 생기므로 용량은 언어당 약 +33%.
**역색인은 필드마다 독립된 표다.** 두 필드에 같은 단어가 있어도 서로 다른 표라 섞이거나 중복되지 않는다. 결과는 문서 단위라 두 필드에서 모두 맞아도 한 번만 나온다.
## 검색은 필드를 지정하는 것뿐 — ES가 언어를 판별하지 않는다
```python
"fields": ["content", "content.ja"]   # 둘 다 뒤짐. 언어 감지 없음
```
`도마뱀` 검색 → nori 필드는 `[도마뱀]`이 있어 매칭, kuromoji 필드는 저장된 게 `[도마뱀의]`라 불일치. **맞는 쪽에서만 결과가 나오고**, 점수도 맞는 쪽이 높게 나와 상위에 정렬된다.
## 그럼 한국어 검색이 왜 한국어 필드에서 나오나 — "점수보다 매칭 여부가 먼저"
흔한 오해: "점수가 높은 언어 필드가 선택된다." 반만 맞다.
1. **결과에 들어갈지 말지는 "매칭이 되느냐"가 정한다.** `도마뱀` 검색 → kuromoji 필드엔 `[도마뱀의]`만 있어 아예 안 맞음 → 점수가 낮은 게 아니라 **후보에 들어오지도 않는다**.
2. **점수는 이미 들어온 것끼리 순서를 정할 때만 쓴다.**
3. 점수 경쟁이 실제로 벌어지는 건 **두 필드 다 맞았을 때**다. 그때 `best_fields`가 둘 중 높은 점수를 그 문서의 점수로 채택한다.

## 사전에 없는 언어를 만나면 — 미등록어(unknown word)
형태소 분석기는 사전에 없는 문자를 만나면 **문자 종류가 바뀌는 지점을 경계 삼아 망핑이로** 자른다. 단어를 이해해서가 아니라 사전이 없으니 그냥 덩어리로 넣는 것.
온라인 kuromoji 데모에 `도마뱀의 서식지`를 넣었더니:
```javascript
도마뱀의   記号,一般   (기호, 일반)
(공백)     記号,空白
서식지    記号,一般
```
품사가 명사가 아니라 **기호(記号)**. 일본어 분석기가 한글을 "모르는 문자 덩어리"로 처리한 증거다.
해롭지는 않다 — ik처럼 한 글자씩 썩병 썬어서 엉뚱한 문서를 끌어오는 일은 없고, 그저 조용히 0개를 반환할 뿐이다.

## 실무 판단으로 배운 것
- **플러그인 설치는 ES 재기동이 필요하지만, 필드 추가는 필요 없다.** 그래서 당장 안 쓸 언어라도 플러그인을 미리 깔아두면 나중에 재기동 없이 대응할 수 있다.
- 영어는 띄어쓰기가 곧 단어 경계라 어떤 analyzer를 쓰든 잘 동작한다. 문제가 되는 건 한·중·일처럼 띄어쓰기로 단어를 구분하지 않는 언어들이다.
- 언어가 진짜 뒤죽박죽이면 언어별 필드보다 내장 `cjk`(두 글자씩 묶기) 하나가 관리상 나을 수 있다. 주력 언어가 1\~2개일 때 언어별 필드가 이득.
