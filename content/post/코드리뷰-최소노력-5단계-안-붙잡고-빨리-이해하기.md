모든 변경 줄을 같은 깊이로 읽기보다, 변경 종류와 영향 범위를 먼저 파악하면 리뷰를 빠르게 시작할 수 있다.

## 다섯 단계

1. **변경 종류를 분류한다.** 기능 추가, 버그 수정, 삭제, 이동, 리팩터링 중 무엇인가?
2. **파일 목록과 변경량을 본다.** 어떤 레이어와 테스트가 바뀌었는지 확인한다.
3. **위험한 경계를 고른다.** 공개 API, 데이터 쓰기, 권한, 비동기 작업처럼 영향이 큰 곳부터 본다.
4. **설명을 코드와 테스트로 대조한다.** 특히 “더 이상 호출하지 않는다” 같은 주장은 사용처 검색으로 확인한다.
5. **변경 종류에 맞게 결론을 낸다.** 수정 코드와 회귀 테스트, 누락된 연결이 핵심이다.

## 변경별 확인 질문

| 변경 종류 | 확인할 내용 |
| --- | --- |
| 기능 추가 | 새 동작과 권한 범위가 맞는가? |
| 버그 수정 | 재현 사례와 정상 동작을 모두 다루는가? |
| 삭제 | 남은 사용처가 없는가? |
| 이동 | 이전 경로 참조가 남지 않았는가? |
| 리팩터링 | API, 상태 전이, 작업 이름, 테스트가 유지되는가? |

삭제나 파일 이동이 큰 변경이라면, 제거된 코드보다 대체 경로와 재배선 부분에 집중한다. 외부 동작이 유지되는지 확인할 수 있는 작은 테스트나 출력 비교를 찾는다.

보안 민감 작업에서는 두 가지부터 확인한다. 요청자가 자기 자원만 다룰 수 있는가? 사용자 입력이 안전하게 바인딩되는가?

리뷰 의견은 관찰한 사실과 확인 질문으로 전달하면 의도를 단정하지 않고도 문제를 분명히 제기할 수 있다.
